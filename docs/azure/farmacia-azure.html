Decisiones

Container Apps para los cuatro servicios
Corre las mismas imágenes del compose. Tiene ingress interno para que el server no quede expuesto, Jobs para las migraciones y escalado a cero en lo que no necesita estar encendido.
mobile-web sigue siendo un contenedor con Caddy
Mantiene el proxy al mismo origen, del que depende la cookie de sesión de Better Auth.
Red privada para los datos
Postgres en subred delegada y Redis por endpoint privado. Cuesta ~US$ 8 al mes y evita abrir los firewalls a "cualquier servicio de Azure".
Secretos en Key Vault con identidad gestionada
Las apps leen DATABASE_URL, REDIS_URL, BETTER_AUTH_SECRET y SMTP_URL como referencias a Key Vault. Ningún secreto queda en el workflow.
Static Web Apps para mobile-web
El plan Free no puede reenviar a un backend, y el cruce de origen rompe las cookies SameSite=Lax. El backend enlazado exige Standard (US$ 9).
App Service B1
Sale ~US$ 13 fijos y sin arranques en frío, pero el server quedaría público y no hay Jobs para migrar.
Azure Functions
No sirve para un worker de BullMQ que corre de forma permanente ni para un servidor Fastify.

Ajustes para Container Apps

  1. Caddyfile: reescribir el Host hacia el server

    El ingress de Container Apps enruta por Host. Si Caddy conserva el Host público, la petición vuelve a ca-farm-web. Hay que agregar header_up Host {upstream_hostport} (X-Forwarded-Host sigue llegando).

  2. Build del admin con API_INTERNAL_URL=http://ca-farm-server

    Queda fijo en el build, así que el workflow lo pasa como build arg.

  3. URLs de conexión gestionadas

    DATABASE_URL con sslmode=require y REDIS_URL=rediss://…:10000. Hay que confirmar que BullMQ funciona en Managed Redis sin modo cluster.

  4. Auth y orígenes

    BETTER_AUTH_URL = URL de web. TRUSTED_ORIGINS = web, admin y bnp://. TRUST_PROXY_ADDRESSES se mantiene, porque los proxies de Azure usan IPs privadas de la VNet. Después del despliegue hay que verificar que el rate limiting vea la IP real del cliente.

  5. Email con ACS

    El usuario SMTP requiere un registro de aplicación en Entra ID. EMAIL_FROM queda como DoNotReply@<id>.azurecomm.net.

  6. Infra y pipeline nuevos en el repo

    infra/main.bicep con sus módulos, infra/main.bicepparam y .github/workflows/deploy-qa.yml, que se dispara solo con push a QA. Más un job opcional de seed con datos sintéticos.

  7. Registrar Microsoft.Cache en la suscripción

    El proveedor de Managed Redis no está registrado todavía en la suscripción de destino.

Riesgos y puntos abiertos

  • Arranque en frío

    Con escalado a cero, la primera visita tarda ~5–15 s. Para presentar al PO se activa el modo demo con un parámetro y después se apaga.

  • Redis B0 es un SKU nuevo

    Admite NoCluster y NoEviction, que es lo que necesita BullMQ. El precio final está por confirmar. El plan B es Redis en un contenedor de ACA con disco, sin SLA, por ~US$ 3.

  • Imágenes privadas en GHCR

    Si el repo es privado, Container Apps necesita un token con read:packages guardado en Key Vault. Si los paquetes son públicos, no hace falta.

  • Conexiones de Postgres

    B1ms admite ~35 conexiones de usuario. Por eso el server tiene máximo 1 réplica.

  • Región

    La suscripción no permite PostgreSQL Burstable en East US 2, así que red, datos y apps van en Central US. Key Vault, identidad y logs quedaron en East US 2.

Ambientes y ramas

DEV integra el trabajo del equipo y solo corre CI. QA despliega este ambiente de pre-producción en Azure, donde el PO valida cada entrega. main queda reservada para producción, que tendrá su propio resource group y se desplegará con los mismos módulos Bicep y otros parámetros. Los cambios avanzan DEV → QA → main.
